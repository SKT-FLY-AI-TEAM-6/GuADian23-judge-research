## 위험 등급 검증 방식과 정확도 지표

GuADian의 위험 등급 판정은 `server/eval_set.json`에 고정된 라벨 데이터를 기준으로 검증합니다. 각 URL에 사람이 먼저 기대 등급을 부여하고, `server/eval.py`가 실제 서버의 `/judge` 응답과 비교해 정확도, 오탐, 약한 판정, 실패, 소요 시간을 집계합니다.

- 관련 문서: [위험 등급 판정 근거](risk-grade-rationale.md)
- 라벨 데이터: [server/eval_set.json](../server/eval_set.json)
- 평가 스크립트: [server/eval.py](../server/eval.py)

---

### 01. 검증 목적

검증의 목적은 단순히 정답률을 계산하는 것이 아니라, 위험 등급 체계가 설계 원칙대로 작동하는지 확인하는 것입니다.

1. 정상 사이트를 불필요하게 막지 않는가
2. 개인정보 입력, 상담 유도, 확인 불가 상황을 `MEDIUM`으로 남기는가
3. 사칭, 차단 목록, 악성 설치 유도처럼 명확한 위험을 `HIGH`로 차단하는가
4. 서버 오류, LLM 실패, 시간 초과를 `UNKNOWN`으로 분리하는가
5. 앱 쉴드의 시간 예산인 12초 안에 판정이 끝나는가

배정 기준은 확실성 · 피해 심각도 · 신원 확인입니다. 따라서 검증 데이터에는 공식 로그인처럼 신원이 확인된 정상 케이스, 표 밖 로그인처럼 신원이 불명확한 중위험 케이스, 사칭 도메인처럼 신원 불일치가 명확한 고위험 케이스를 함께 포함합니다.

---

### 02. 검증 데이터 구성

현행 검증 세트는 총 45개 URL입니다. 실제 광고 도착지, 팀이 실기기에서 만난 오판 사례, 차단 목록 도메인, 공식 사이트 예외 케이스를 함께 포함합니다.

| 기대 등급 | 건수 | 비율 | 검증 목적 |
| :-- | :-: | :-: | :-- |
| `LOW` | 36 | 80.0% | 공식 사이트, 언론사, 정상 쇼핑몰, 광고 기술 회사 등 정상 도착지의 오탐 확인 |
| `MEDIUM` | 6 | 13.3% | 개인정보 입력 폼, 상담 유도, 확인 불가 페이지처럼 선택권을 남겨야 하는 상황 확인 |
| `HIGH` | 3 | 6.7% | 차단 목록 도메인, 사칭 도메인, 명확한 고위험 도착지 차단 확인 |
| 합계 | 45 | 100% | 정상·중위험·고위험·판정 실패 계열을 포함한 회귀 검증 |

고위험 샘플은 3건뿐이므로 고위험 재현율을 통계적으로 일반화하지 않습니다. 실제 피싱·사칭 도메인은 수명이 짧아 장기 검증 세트에 안정적으로 남기기 어렵기 때문입니다. 대신 사칭, APK, 비밀번호 폼 같은 고위험 로직은 `server/test_agent.py`의 오프라인 가짜 페이지 테스트로 별도 검증합니다.

### 04. 측정 지표

`eval.py`는 각 URL의 기대 등급과 실제 응답 등급을 비교하고, 다음 지표를 출력합니다.

| 지표 | 의미 | 해석 |
| :-- | :-- | :-- |
| 맞춤 | 기대 등급과 실제 `risk`가 일치한 건수 | 전체 정확도 |
| 약함 | 기대 `HIGH`가 실제 `MEDIUM`으로 나온 경우 | 차단해야 할 위험을 경고 수준으로 낮게 본 사례 |
| 오탐 | 기대 `LOW`가 실제 `MEDIUM` 또는 `HIGH`로 나온 경우 | 정상 도착지를 불필요하게 경고하거나 차단한 사례 |
| 실패 | `UNKNOWN`, 타임아웃, 무응답 등 판정 자체를 완료하지 못한 경우 | 정확도 실패와 별도로 관리해야 하는 운영 안정성 지표 |
| 중앙값 | 전체 케이스 소요 시간의 중앙값 | 일반 사용자가 체감하는 보통 판정 시간 |
| p90 | 90% 케이스가 이 시간 안에 끝나는 기준 | 느린 케이스의 상한 확인 |
| 최대 | 가장 오래 걸린 단일 케이스 | 최악 지연 확인 |
| 12초 초과 | 앱 쉴드 타임아웃 기준을 넘긴 건수 | 사용자에게 확인 불가 화면이 뜰 수 있는 케이스 |

GuADian은 사용자 선택권 보존을 중요한 원칙으로 두기 때문에, 단순 정확도뿐 아니라 오탐을 별도 지표로 분리합니다. 정상 도착지를 위험하다고 판단하면 사용자의 정상적인 선택을 제한할 수 있기 때문입니다.

### 07. 재현 방법

로컬 서버 기준 검증:

```bash
cd server
python eval.py --server http://127.0.0.1:8000 --fresh
```

배포 서버 기준 검증:

```bash
cd server
python eval.py --server https://adalert-judge.azurewebsites.net --fresh
```

저위험 선행 통보까지 포함한 스트리밍 검증:

```bash
cd server
python eval.py --server http://127.0.0.1:8000 --fresh --stream
```

`--fresh` 옵션은 서버 캐시를 무시하고 매번 새로 판정하기 위한 옵션입니다. 속도와 정확도를 비교할 때는 캐시 적중으로 인한 왜곡을 줄이기 위해 `--fresh` 기준을 사용합니다.
