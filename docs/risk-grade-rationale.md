### 01. 요약

GuADian의 위험 등급 체계는 다음 흐름으로 구성됩니다.

1. 설계 원칙: 사용자 선택권 보존과 불필요한 차단 최소화
2. 근거 출처: 법령, 정부기관 안내, 플랫폼 정책, 국제 보안 UI 기준에 기반한 위험 신호 도출
3. 등급 체계: W3C 보안 UI 가이드를 참고한 `LOW`/`MEDIUM`/`HIGH`/`UNKNOWN` 개입 수준 구분
4. 배정 기준: 확실성 · 피해 심각도 · 신원 확인 기준에 따른 위험 신호별 등급 배정
5. 예외 처리: 페이지 확인 불가, 서버 오류, LLM 실패, 전체 시간 초과 등 판정 실패 상황의 처리
6. 판정 안전장치: 정해진 등급과 위험 유형 목록 안에서만 판단하도록 하는 구조적 제한
7. 검증 방식: `eval_set.json`의 기대 등급과 서버 응답 등급 대조를 통한 실제 적용 결과 확인

따라서 이 체계에서 자체 판단이 개입되는 지점은 "무엇을 위험 신호로 볼 것인가"가 아니라, 공식 출처에서 확인된 위험 신호를 어떤 개입 수준에 배정할 것인가입니다. 이 배정은 확실성 · 피해 심각도 · 신원 확인 기준에 따라 일관되게 적용됩니다.

### 02. 설계 원칙

위험 등급 체계는 두 가지 전제를 바탕으로 설계됩니다.

1. 사용자의 정상적인 선택은 가능한 한 제한하지 않아야 합니다.
2. 개인정보 유출, 악성 앱 설치, 금전 피해처럼 회복이 어려운 피해는 강하게 차단해야 합니다.

따라서 GuADian의 기본 원칙은 사용자 선택권 보존, 불필요한 차단 최소화입니다. 모든 의심 상황을 일괄 차단하면 정상적인 이용까지 제한될 수 있고, 반대로 모든 상황을 통과시키면 보호 기능의 실효성이 낮아집니다. GuADian은 이 균형을 맞추기 위해 위험 신호의 강도와 확실성에 따라 개입 수준을 구분합니다.

### 03. 근거 출처

위험 신호 자체는 임의로 설정하지 않습니다. 법령, 정부기관 안내, 플랫폼 정책, 국제 보안 UI 기준 등 공식 출처에서 반복적으로 위험 요소로 제시되는 항목을 판정 근거로 사용합니다.

대표적으로 다음과 같은 신호를 위험 판단의 근거로 사용합니다.

- 브랜드 사칭과 도메인 불일치
- 주민등록번호, 카드번호 등 민감정보 요구
- 공식 앱스토어 외부의 APK 설치 유도
- 차단 목록 적중
- 로그인 폼 또는 개인정보 입력 폼
- 사업자 정보가 불명확한 결제 유도
- 당첨, 무료, 한정 등의 과도한 유인 문구
- 투자, 고수익, 원금 보장성 권유
- 콘텐츠팜성 페이지
- 페이지 확인 불가 또는 판정 실패

### 04. 등급 체계

| 등급 | 의미 | 개입 방식 |
| :-- | :-- | :-- |
| `LOW` | 확인 가능한 위험 신호가 없음 | 통과 |
| `MEDIUM` | 위험 가능성은 있으나 확정하기 어려움 | 선택지를 남기고 한 번 더 확인 |
| `HIGH` | 명확히 확인된 위험이 있고 피해 심각도가 높음 | 차단 |
| `UNKNOWN` | 서버 오류, LLM 실패, 전체 시간 초과 등으로 판정 자체가 실패 | UI에서는 `MEDIUM` 수준으로 개입 |

이 구조는 오탐이 사용자의 정상적인 선택을 과도하게 제한할 수 있다는 문제의식에서 출발합니다. 확정되지 않은 위험은 즉시 차단하지 않고 사용자에게 선택지를 남기며, 명확하고 피해가 큰 위험에 대해서만 강한 개입을 적용합니다.


판정 근거가 위험 신호의 출처를 정의한다면, 등급 체계는 해당 신호에 대해 사용자에게 어느 정도의 개입을 적용할지 결정합니다.

GuADian은 W3C WSC-UI의 보안 UI 가이드를 참고합니다. W3C WSC-UI는 위험 상황에서 사용자에게 제시할 경고 수준을 크게 `Warning/Caution`과 `Danger`로 구분합니다. GuADian은 이를 다음과 같이 매핑합니다.

| 기준 | 의미 | GuADian 등급 |
| :-- | :-- | :-- |
| 위험 등급 아님 | 위험 신호가 없거나 개입 근거가 없음 | `LOW` |
| `Warning/Caution` | 위험 가능성은 있으나 확정하기 어려움 | `MEDIUM` |
| `Danger` | 명확히 확인된 위험 | `HIGH` |
| 판정 실패 | 서버 오류, LLM 실패, 전체 시간 초과 | `UNKNOWN` |

W3C는 위험 상황에서 경고를 어떻게 제시할지에 대한 원칙을 제공합니다. 다만 "개인정보 입력 폼은 `MEDIUM`이다" 또는 "APK 직접 다운로드는 `HIGH`다"처럼 개별 신호를 앱의 등급 체계에 직접 배정하지는 않습니다.

따라서 등급 체계의 구조는 W3C 기준을 참고하되, 개별 신호의 등급 배정은 다음 배정 기준에 따라 결정합니다.

### 05. 배정 기준

배정 기준은 공식 출처에서 확인된 위험 신호를 실제 등급으로 연결하기 위한 내부 기준입니다. 공식 출처는 위험 신호를 제시하고, W3C는 개입 강도를 구분하는 틀을 제공합니다. 그러나 특정 신호를 `LOW`, `MEDIUM`, `HIGH` 중 어디에 배정할지는 별도의 판단 기준이 필요합니다.

GuADian은 다음 세 기준으로 등급을 배정합니다.

| 기준 | 질문 | 역할 |
| :-- | :-- | :-- |
| 확실성 | 코드와 도구 결과로 위험 신호가 확인됐는가 | 오탐 방지 · 근거가 없으면 `HIGH` 불가 |
| 피해 심각도 | 금전 이동, 계정 탈취, 기기 장악, 변경 불가 신원정보 유출로 이어질 수 있는가 | 개입 강도 결정 · 해당하지 않으면 `MEDIUM` 상한 |
| 신원 확인 | 공식 도메인 표 또는 신뢰 가능한 출처로 사이트 신원이 확인됐는가 | 사칭 가능성 제거 · 공식 신원이 확인되면 사칭 기반 위험 완화 |

실제 판정은 아래의 신원 × 행동 구조로 설명할 수 있습니다. 이 표가 코드에 그대로 하드코딩된 것은 아니며, `CRITERIA` 프롬프트, `BRANDS` 공식 도메인 표, 도구 결과, 고위험 근거 검증이 결합되어 같은 판단 구조를 구현합니다.

| 신원 ↓ · 행동 → | 열람만 | 로그인·회원가입 | 연락처 수집 | 결제·가입 | 주민번호·카드 요구 | APK 설치 |
| :-- | :-- | :-- | :-- | :-- | :-- | :-- |
| 악성 목록 등재 | `HIGH` | `HIGH` | `HIGH` | `HIGH` | `HIGH` | `HIGH` |
| 사칭 확정 | `HIGH` | `HIGH` | `HIGH` | `HIGH` | `HIGH` | `HIGH` |
| 공식 확인 | `LOW` | `LOW` | `MEDIUM` | `LOW` | `LOW` | `MEDIUM` |
| 정체 불명 | `LOW` | `MEDIUM` | `MEDIUM` | 사업자 있음 `LOW` · 없음 `MEDIUM` | `HIGH` | `HIGH` |
| 확인 불가 | 표에 있으면 `LOW` · 없으면 `MEDIUM` 또는 `UNKNOWN` | 행동 판별 불가 | 행동 판별 불가 | 행동 판별 불가 | 행동 판별 불가 | 행동 판별 불가 |

표 해석 기준은 다음과 같습니다.

- 악성 목록 등재와 사칭 확정은 행동을 보기 전에 신원만으로 `HIGH` 판정
- 공식 확인은 사칭 가능성을 제거하므로 로그인·회원가입·정상 결제는 `LOW`
- 공식 사이트라도 연락처 수집은 영업 연락 가능성이 있어 `MEDIUM`
- 공식 사이트라도 스토어 밖 APK는 스토어 검증을 우회하므로 `MEDIUM`
- 정체 불명 사이트의 주민번호·카드 요구와 APK 설치는 피해 심각도가 높아 `HIGH`
- 확인 불가는 본문을 읽지 못해 행동 판별이 어려우므로 예외 처리 기준 적용

판정은 다음 순서로 이루어집니다.

| 조건 | 등급 |
| :-- | :-- |
| 확인 결과 위험 신호 없음 | `LOW` |
| 위험 신호는 있으나 확실성이 낮음 | `MEDIUM` |
| 확실한 위험 신호가 있으나 피해 심각도가 낮거나 신원 확인으로 사칭 가능성이 제거됨 | `MEDIUM` 상한 |
| 확실한 위험 신호 + 높은 피해 심각도 + 신원 불일치 또는 차단 목록 적중 | `HIGH` |

즉, `HIGH`는 단순히 "위험해 보이는 경우"가 아니라 근거가 확인되고, 피해 심각도가 높으며, 신원 불일치 또는 차단 목록처럼 강한 근거가 있을 때만 부여합니다. 위험 신호가 있더라도 확실성이 낮거나 공식 신원으로 사칭 가능성이 제거되면 사용자의 선택권을 보존하기 위해 `MEDIUM` 이하로 제한합니다.

| 신호 | 확실성 | 피해 심각도 | 신원 확인 | 등급 |
| :-- | :-: | :-: | :-: | :-- |
| 사칭: 표 내 브랜드 자처 + 도메인 불일치 | O | O | 불일치 | `HIGH` |
| 주민번호·카드번호 요구 | O | O | 미확인 | `HIGH` |
| 스토어 밖 APK | O | O | 미확인 | `HIGH` |
| 차단 목록 적중 | O | O | 무관 | `HIGH` |
| 공식 도메인 로그인 폼 | O | O | 확인 | `LOW` |
| 표 밖 로그인 폼 | O | O | 미확인 | `MEDIUM` |
| 공식 사이트의 스토어 밖 APK | O | O | 확인 | `MEDIUM` |
| 개인정보 입력 폼 | O | 보통 | 미확인 | `MEDIUM` |
| 사업자 정보 없는 결제 | 부분 | O | 미확인 | `MEDIUM` |
| 당첨·무료·한정 | 부분 | 낮음 | 미확인 | `MEDIUM` |
| 투자·고수익 권유 | 부분 | O | 미확인 | `MEDIUM` |
| 콘텐츠팜 | 부분 | 낮음 | 미확인 | `MEDIUM` |
| 페이지 확인 불가 | - | - | - | 예외 처리 기준 적용 |

### 06. 예외 처리

일부 상황은 페이지의 위험성을 직접 판단하기보다, 판정 가능 여부 자체를 먼저 처리해야 합니다. 이 경우 사용자를 즉시 차단하기보다, 확인 실패의 성격에 따라 보수적으로 개입합니다.

| 상황 | 처리 등급 | 처리 방식 |
| :-- | :-- | :-- |
| 페이지 확인 불가 | `MEDIUM` | 위험을 확정하지 않고 사용자에게 한 번 더 확인 |
| 서버 오류 | `UNKNOWN` | 판정 실패로 처리하고 UI에서는 `MEDIUM` 수준으로 개입 |
| LLM 실패 | `UNKNOWN` | 판정 실패로 처리하고 UI에서는 `MEDIUM` 수준으로 개입 |
| 전체 시간 초과 | `UNKNOWN` | 판정 실패로 처리하고 UI에서는 `MEDIUM` 수준으로 개입 |

`UNKNOWN`은 위험이 확인됐다는 뜻이 아니라, 정상적인 판정이 완료되지 않았다는 뜻입니다. 따라서 UI에서는 `HIGH`처럼 즉시 차단하지 않고 `MEDIUM` 수준의 확인 절차로 연결합니다.

### 07. 판정 안전장치

판정 안전장치는 앞서 정의한 기준이 실제 실행 과정에서 이탈하지 않도록 하는 장치입니다. 위험 판정은 에이전트가 자유롭게 작성하는 문장이 아니라, 정해진 형식과 목록 안에서만 생성됩니다.

- 모델의 최종 등급은 `LOW`, `MEDIUM`, `HIGH`만 사용할 수 있고, 서버 실패는 `UNKNOWN`으로 처리됨
- 위험 유형은 미리 정의된 목록에서만 선택 가능
- 근거 없는 위험 유형을 새로 만들 수 없음
- 고위험 신호는 코드에서 별도로 검증함
- 차단 목록 적중처럼 외부에서 확정 가능한 신호는 LLM 판단 없이 즉시 처리

이를 통해 에이전트가 임의의 위험 유형을 생성하거나, 판정 근거 밖의 등급을 부여하는 상황을 제한합니다. 특히 `HIGH`처럼 사용자를 직접 차단하는 결과는 근거가 명확한 경우에만 도출되도록 통제합니다.


---

### 08. 검증 방식

검증 방식은 판정 안전장치가 실제 결과에서도 의도대로 작동하는지 확인하는 절차입니다. 형식 제어만으로는 판정의 정확성을 보장할 수 없기 때문에, 실제 사이트를 대상으로 판정 결과를 사람이 직접 검수합니다.

검증은 `server/eval_set.json`의 라벨 데이터와 `server/eval.py`로 재현합니다. 현행 검증 세트는 총 45건이며, `LOW` 36건, `MEDIUM` 6건, `HIGH` 3건으로 구성됩니다. 2026-08-24 7차 평가 기준 현행 서버는 `37/45` 일치, 중앙값 `3.6s`, p90 `5.4s`, 최대 `7.3s`, 12초 초과 `0건`, `UNKNOWN` 1건을 기록했습니다.

정확도, 오탐, 약한 판정, 실패, 차수별 변화, 재현 명령은 별도 문서인 [위험 등급 검증 방식과 정확도 지표](risk-grade-validation.md)에 정리합니다.

시스템은 다음 두 단계로 통제됩니다.

- 판정 안전장치: 판정이 정해진 형식과 목록을 벗어나지 않도록 제한
- 검증 방식: `eval_set.json`의 기대 등급과 서버 응답 등급을 자동 대조하고, 불일치 사례는 사람이 원인 분석
