### 02. 판정 구조: 세 번의 변경

광고 도착지를 판정하는 서버 구조를 세 번 바꿨습니다. 출처: [judge_agent.py#L1-L20](../server/judge_agent.py#L1-L20), [judge_agent.py#L654-L656](../server/judge_agent.py#L654-L656), [main.py#L414-L416](../server/main.py#L414-L416)

| 버전 | 방식 | 막힌 이유 (실측) | 결과 |
| :-- | :-- | :-- | :-- |
| v1 고정 파이프라인 (`main._ask_llm`) | 코드가 정한 순서 하나. 페이지 1번 읽기 → Claude에 1번 묻기 | 본문이 비면(JS 렌더링, 리다이렉트 껍데기) "확인 못 함"으로 종료. "KB국민은행"이 적힌 `kb-star.top`은 글자만으로 사칭 판별 불가 | 폐기 |
| v2 도구 에이전트 | Claude가 도구 종류, 개수, 순서를 결정. 코드는 예산(도구 3회, 7.5초), 근거 검증, 출력 스키마만 강제 | 72건 실측(2026-08-23): 46%가 왕복 2회 이상. 추가로 부른 도구 대부분이 `page_signals`, `domain_age`, `official_domain_of`로 전부 미리 모을 수 있는 것 | 비교, 비상용으로 유지 (`JUDGE_ONESHOT=0`) |
| v3 왕복 1회 + 병렬 프리페치 | 페이지 본문, 페이지 신호, 차단 목록, 전 판정, 공식 도메인, 도메인 등록일을 4.5초 안에 병렬 수집해 첫 질문에 전부 포함. Claude 호출 1회 | eval 42건 캐시 없이: 에이전트 32/42, 중앙값 4.4s, p90 7.7s ↔ 왕복 1회 33/42, 3.8s, 5.7s | **채택 (현행)** |

v2에서 v3로 가며 유지한 것: "운전대는 Claude, 가드레일은 코드" 원칙. 고위험 근거가 도구 결과 원문에 없으면 `MEDIUM`으로 강등하는 근거 검증(`_ground`)과 `final_verdict` 스키마 강제는 v3에도 그대로 남았습니다.

"답을 아는 것은 묻지 않음" 사례 ([judge_agent.py#L746-L753](../server/judge_agent.py#L746-L753)): 본문이 비면 모델이 첫 바퀴에 `official_domain_of`를 부르는데 그 답은 이미 서버 표에 있었습니다. 그 왕복 한 번이 앱 시한을 넘기게 했습니다(실측 hi.co.kr 9.6초 > 9.5초). 미리 조회해 첫 질문에 넣는 것으로 해결했습니다.

#### 구조 버전과 차수 대응

[02. 판정 구조](#02-판정-구조-세-번의-변경)의 v1, v2, v3가 위 차수 표의 어느 행에 해당하는지 대응시킨 표입니다. 구조 이야기는 "무엇을 바꿨나", 차수 표는 "언제, 어떤 순서로, 무엇을 실측하며 바꿨나"를 말합니다.

| 차수 | 구조 | 바꾼 축 | 수치 | 서사에서의 역할 |
| :-- | :-- | :-- | :-- | :-- |
| (표 이전) | v1 고정 파이프라인 | — | 측정 없음 | 정보 부족으로 v2로 교체. eval 이전이라 수치 없음 |
| 0 옛 서버 | **v2** 에이전트 | — | 33/42, 7.3s, p90 11.1s, 12초 초과 6/72 | v2의 문제 발견. "46%가 왕복 2회 이상"이 이 72건에서 나온 수치 |
| 1 | v2 (왕복 1회 플래그 추가) | 구조, 스트리밍 | 측정 불가 | v3 도입 시도. 스트리밍 장애에 묻혀 구조 효과를 못 봄 |
| 2 | v2 | LLM 시한 4s | 27/42, 7.9s | 하락. 구조 탓이 아니라 시한 탓 |
| 3 | v2 | 시한 3s, 재시도 1회 | 30/42, 타임아웃 7 | 악화. 3s < 판정 문장 생성 3.4s |
| 4 | v2 | 측정 추가 | (표본 4) | 단계별 ms 측정으로 숨은 3초 발견 |
| 5 에이전트 | v2 병목 제거 | 26만 행 스캔 제거, lxml | 32/42, 4.4s | v2의 최선 |
| 5 왕복 1회 | **v3** | 구조 (`JUDGE_ONESHOT=1`) | 33/42, 3.8s | v3 채택. 4.4→3.8s가 구조만의 효과 |
| 6 | v3 | 판정 기준(프롬프트) | 38/45 | 구조 고정, 정확도 축 |
| 7 | v3 | 운영(DB 분리) | 37/45, 3.6s | 구조 고정, 안정성 축. 현행 |

두 이야기가 이어지는 방식:

1. 0차가 곧 v2입니다. 구조 절에서 말한 "v2의 문제: 46% 왕복 2회, 12초 초과 6/72"는 차수 표 0차 행과 같은 측정입니다.
2. 1~4차는 v3를 켜지 못한 구간입니다. 왕복 1회 플래그는 1차에 넣었지만 실제로 켠 것은 5차입니다. 그 사이의 하락(27/42, 30/42)은 LLM 시한을 측정 없이 조인 탓이며, 여기서 "시한은 측정 뒤에"가 나와 4차 측정, 5차 병목 제거로 이어집니다.
3. 5차를 두 번 잰 덕에 구조 효과가 분리됩니다. 같은 서버에서 플래그만 바꿔 에이전트 32/42, 4.4s ↔ 왕복 1회 33/42, 3.8s. 0차 대비 7.3→3.8s 가운데 병목 제거 몫(7.3→4.4s)과 구조 몫(4.4→3.8s)을 따로 말할 수 있습니다.

6~7차는 구조가 아니라 다른 축입니다. 구조가 v3로 고정된 뒤 정확도([04. 판정 기준 v2](#04-판정-기준-v2))와 안정성([08. 운영 안정성](#08-운영-안정성))을 손본 것입니다.

### 05. 오탐 방지 장치: 실사고와 대응

설계 원칙은 "오탐 하나가 미탐 열보다 나쁨"입니다. 정상 광고가 빨강이면 "광고는 광고일 뿐, 위험한 건 따로 있다"는 앱의 주장이 무너지기 때문입니다. 아래 장치는 전부 실사고에서 나왔습니다. 출처: [judge.md §4](judge.md#4-오탐-방지-장치)

### 07. 검색 결과 배지

검색 결과 화면의 위험 배지는 규칙이 먼저 결론을 내고, 결론이 안 나는 것만 판별기에 넘깁니다. 규칙만으로 종결할 경계를 두 값으로 검증했습니다. 출처: [SerpRules.kt#L18-L30](../app/src/main/java/com/flyai/adalert/serp/SerpRules.kt#L18-L30)

| 경계 | 규칙 종결 | 문제 | 판단 |
| :-- | :-- | :-- | :-- |
| '주의'(40) | 25/27 | APK 직접 배포 사이트, IP 직결 무료영화 사이트가 '주의'로 확정. 둘 다 판별기 기준 90점대 '위험'. 규칙 확정 항목은 판별기가 못 보므로 오판 시 수정 기회 없음 | 폐기 |
| '위험'(70) | 15/27 | 오답 0 | **채택** |

표본 27건, 2026-08-14. 비용은 거의 같습니다. 판별기 호출은 항목당이 아니라 화면당 1회라 판별기행 항목이 2개든 12개든 호출 수가 동일하기 때문입니다.

판별기 구현은 현재 규칙 전용(`RuleOnlyClassifier`)이며, AI 판별기는 인터페이스(교체점)만 남아 있습니다 ([SerpClassifier.kt](../app/src/main/java/com/flyai/adalert/serp/SerpClassifier.kt)).
